# HydroDesk 端到端闭环评审与 6 Case 下一步规划（2026-04-07）

## 1. 评审范围与目标

本次评审目标不是单纯检查算法精度，而是回答一个更大的平台问题：

> 现有仓库是否已经具备“基于 HydroDesk，从数据源目录到成果报告”的工程级端到端闭环能力，并能承载以下 6 个 case：

- 中线
- 胶东调水
- 徐洪河
- 引绰济辽
- 大渡河
- 雅鲁藏布江下游水电工程

本次结论基于对以下范围的覆盖式审查：
- 顶层目录结构
- 数值求解核心目录
- HEC-RAS / GIS / EPANET / SWMM 集成目录
- Web 前后端与报告链
- `validation_cases/`、`hecras_all_cases/`、`scripts/`
- 关键入口文件、关键示例、关键报告/状态文件

---

## 2. 总结结论

## 2.1 一句话结论

**当前仓库还不具备面向这 6 个工程 case 的 HydroDesk 端到端闭环平台能力。**

它目前更接近一个：

- 高强度研究仓
- 多条数值验证链并存
- HEC-RAS 对标工具链
- Web 工作台原型
- 报告/分析工具集合

而不是一个已经统一收敛成：

> “工程数据源目录 -> 标准化项目模型 -> 仿真/分析 -> 成果报告”的产品化平台

## 2.2 当前最强能力

当前最成熟、最可用的链路是：

- `HEC-RAS 输入文件`
- `integration/hec_ras_adapter.py`
- `runner.py` / `scripts/run_hecras_deterministic_workflow.py`
- 求解器与对标输出
- JSON/Markdown/报告桥落盘

也就是说，仓库当前最强的是：

**HEC-RAS 输入驱动的研究/对标闭环**

而不是：

**HydroDesk 面向工程项目的数据治理 + 建模 + 仿真 + 报告闭环**

---

## 3. 全仓结构评审

## 3.1 目录层面现状

仓库整体呈现 4 条主线并存：

### A. 数值求解内核
- `solvers/`
- `physics/`
- `core/`

特点：
- 实现深、能力广
- 含稳态、非恒定、河网、压力管网、水工结构、水锤等
- 是整个仓库最硬核、最有积累的部分

### B. HEC-RAS / 外部模型适配与验证
- `integration/`
- `runner.py`
- `scripts/`
- `validation_cases/`
- `hecras_all_cases/`

特点：
- 已形成明确的输入提取、对标、报告、验证脚本体系
- 对 HEC-RAS 工作流复刻意识很强
- 这是目前最接近“闭环”的部分

### C. Web / 工作台原型
- `web/frontend/`
- `web/backend/`
- `webapp/`
- `api/`
- `backend/`

特点：
- 存在多代实现并存
- 有前端工作台、后端 API、结果分析、导出等雏形
- 但尚未统一成唯一、清晰、可信赖的平台主入口

### D. 文档 / 交付 / 历史产物
- 顶层大量 `🎯/🎊/🏆/...` 报告文件
- `tmp/`
- `backups/`
- 各类中间测试和阶段性总结

特点：
- 信息量大，但噪音高
- 对交接不友好
- 会显著增加后续开发与检索成本

## 3.2 目录级问题清单

### 问题 1：平台主入口不唯一
- 既有 `hydroclaude_cli.py`
- 又有 `runner.py`
- 又有 `web/backend/api_gateway`
- 又有 `api/rest_server.py`
- 还存在 `webapp/` 与 `web/frontend/` 两套前端痕迹

影响：
- 后续要做 HydroDesk 平台时，很难回答“到底以哪条链为正统”

### 问题 2：顶层文档与产物高度堆积
- 顶层存在大量阶段性报告、庆祝文件、测试结果和临时总结
- 对“全面评审”和“工程交接”非常不利

影响：
- 降低可维护性
- 干扰代码检索
- 新对话极易误判项目成熟度

### 问题 3：研究链与产品链没有真正统一
- 求解器侧很强
- Web 工作台侧有演示与原型
- 但两者之间缺少“项目级数据模型 + case 注册 + 报告规范”的统一骨架

## 4. 现有端到端闭环能力判断

## 4.1 已存在的闭环

### 闭环 A：HEC-RAS 对标闭环

当前已具备：
- 输入：HEC-RAS `.prj/.g0*/.f0*/.p0*` 及输入侧 HDF
- 解析：`integration/hec_ras_adapter.py`
- 参数构建：`build_solver_params_from_inputs`
- 执行：`HydroClaudeRunner` / `HydroClaudeSimulator`
- 对比：HEC-RAS 参考结果用于验证
- 落盘：JSON、报告、workflow contract

结论：
- **这条链是当前最完整的闭环**

### 闭环 B：Web 配置驱动的简化仿真闭环

当前可见链路：
- 前端配置表单 / 组件建模
- API 提交仿真
- `SimulationService`
- `HydraulicEngineV2`
- `result_store`
- `/analysis/result` 返回 `markdown_report`

结论：
- **这是“配置 -> 仿真 -> 结果分析”的轻量闭环**
- 但它还不是“工程数据源目录 -> 成果报告”的闭环

## 4.2 尚未形成的闭环

### 缺口 1：数据源目录接入层不完整
- 前端有 `DataImporter.tsx`，但更像演示 UI
- 没看到真正稳定的上传解析 API 闭环
- 没看到针对“工程目录”的标准抽取、校验、注册、建模入库流程

### 缺口 2：项目级标准数据模型缺失
- 缺少统一的 `Project / Case / Scenario / Asset / SourceDirectory / ReportArtifact` 模型
- 当前更多是脚本和配置在直接驱动

### 缺口 3：工程报告链不统一
- 有本地报告器
- 有分析 API
- 有 MCP 报告桥
- 但没有统一的“工程项目成果报告模板”和版本化产出规则

### 缺口 4：6 个真实工程 case 不在仓内
- 本次检索未发现这 6 个工程的现成数据目录、case metadata、集成入口或报告模板
- 因此现在无法说“平台已具备直接接入并闭环”

## 5. 6 个 Case 能力映射

## 5.1 调水/输水类 Case

包括：
- 中线
- 胶东调水
- 徐洪河
- 引绰济辽

### 业务特征
- 长距离输水
- 多闸、多泵、多渠段/多节点
- 调度与控制约束强
- 需要项目级目录治理、方案管理、运行报告

### 当前仓库匹配能力
- 明渠与非恒定求解：有
- 河网/多 Reach：有
- 泵站/闸门/阀门/渠道结构：有
- 控制/MPC/调度探索：有一些架构和示例
- Web 建模工作台原型：有

### 当前缺口
- 工程目录导入标准：缺
- 项目级输水网络数据模型：缺
- 真实工程 case 模板：缺
- 调水成果报告模板：缺
- SCADA/运行态数据接入规范：缺

### 可行性结论
- **技术内核层面可行**
- **平台闭环层面未完成**

### 优先级建议
- 第一梯队优先做：
  - 中线
  - 引绰济辽

原因：
- 与仓库现有“明渠 + 河网 + 控制”方向更一致
- 能较快把平台能力做成通用骨架

## 5.2 水电/库区类 Case

包括：
- 大渡河
- 雅鲁藏布江下游水电工程

### 业务特征
- 库区、水电站、机组、阀门、调压井、尾水系统
- 可能涉及引水隧洞、压力管道、水锤、调峰调度
- 成果报告更偏水电工况与运行评估

### 当前仓库匹配能力
- 水电站结构原型：有
- 水轮机 / 阀门 / 调压井 / 水库类结构：有
- 压力管网 / 水锤求解：有
- 水电示例脚本：有

### 当前缺口
- 这些能力更多停留在“结构原型 + 示例”
- 尚未见到统一的“水电工程项目模型”
- 尚未看到真实工程数据源目录 -> 仿真 -> 报告的成体系流水线

### 可行性结论
- **组件级能力存在**
- **工程级平台能力明显不足**

### 优先级建议
- 第二梯队推进：
  - 大渡河
  - 雅鲁藏布江下游水电工程

原因：
- 水电类需要先把调水/输水平台骨架稳定，再扩展到更复杂的库区/机组/压力系统

## 6. 核心差距判断

如果目标是“6 个 case 的 HydroDesk 端到端闭环”，当前真正缺的不是再叠更多求解器参数，而是以下平台层能力：

## 6.1 Case 资产治理层
- 数据源目录标准
- case 注册表
- 数据版本与哈希
- 目录扫描与校验
- 资产清单与缺失提示

## 6.2 标准项目模型层
- Case
- Scenario
- Network / Structure / Boundary / Control
- SourceDirectory
- ExecutionRecord
- ReportArtifact

## 6.3 HydroDesk 执行编排层
- 导入
- 标准化
- 仿真编排
- 分析
- 成果报告生成
- 历史版本追踪

## 6.4 报告产品层
- 针对调水工程的报告模板
- 针对水电工程的报告模板
- 统一的成果目录结构
- 一键导出机制

## 7. 下一步规划

## Phase 0：平台收敛与“唯一主线”定义（1-2 周）

### 目标
- 明确 HydroDesk 的唯一主入口和主工作流

### 要做
- 选定一条平台主线：
  - 推荐：`web/backend/api_gateway + web/frontend + runner/integration`
- 明确弃用/冻结的旧入口：
  - `api/`
  - `backend/` 中重复后端实现
  - 非主线原型入口
- 清点并隔离顶层历史报告/噪音文件

### 验收
- 有一份 `HydroDesk 平台主线说明`
- 有一份 `历史入口归档清单`

## Phase 1：6 Case 统一数据模型与目录规范（2-3 周）

### 目标
- 建立“数据源目录 -> 标准项目模型”的统一入口

### 要做
- 定义 `case_manifest.yaml/json` 规范
- 定义数据源目录结构标准
- 为 6 个 case 建立空壳项目模板
- 建立 case registry

### 验收
- 6 个 case 都能被注册与校验
- 即使未能跑仿真，也能完整识别资产、缺口、来源

## Phase 2：HydroDesk 导入链落地（2-4 周）

### 目标
- 真正打通“数据源目录导入”

### 要做
- 后端实现真实导入 API
- 替换前端 `DataImporter` 的模拟逻辑
- 实现：
  - 目录扫描
  - 格式识别
  - 基础校验
  - 入库/注册
  - 失败项反馈

### 验收
- 任一 case 数据目录可导入
- 形成标准项目对象

## Phase 3：仿真编排与成果报告统一（3-4 周）

### 目标
- 从“导入成功”推进到“有结果、有报告”

### 要做
- 打通：
  - Project -> Scenario -> Run
  - Run -> Analysis -> Report
- 统一结果目录规范
- 统一 Markdown/HTML/PDF 报告模板

### 验收
- 至少 1 个调水类 case、1 个水电类 case 跑通“目录 -> 报告”

## Phase 4：先做 2 个样板 Case，再扩 6 个（4-6 周）

### 样板建议
- 调水样板：`中线` 或 `引绰济辽`
- 水电样板：`大渡河`

### 原因
- 一条代表渠道/网络/调度
- 一条代表库区/机组/压力系统

### 验收
- 两类工程至少各 1 个端到端闭环
- 形成可复用模板，再复制到剩余 4 个 case

## Phase 5：6 Case 全覆盖（持续迭代）

### 目标
- 完成 6 case 的批量纳管与报告化

### 验收
- 每个 case 都具备：
  - 数据源目录
  - case manifest
  - 可执行 scenario
  - 成果报告
  - 缺口清单与当前状态

## 9. 最终判断

### 当前能做什么
- 可以继续做 HEC-RAS 输入驱动的验证与研究
- 可以做 Web 原型层的配置仿真与结果分析
- 可以把调水/水电工程所需结构能力逐步拼起来

### 当前不能声称什么
- 不能声称已经有 “HydroDesk 完整工程平台”
- 不能声称已经支持这 6 个工程 case 的端到端闭环
- 不能把前端导入演示能力当成真实工程导入能力

### 结论
- **当前项目适合进入“平台化收敛期”**
- 不适合继续在“多入口、多原型、多阶段性报告并存”的状态下直接扩 6 个工程 case
